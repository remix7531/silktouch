# silktouch

Bidirectional config fragment merger: `combine` folds JSON fragments into one file, `split` routes edits made to that file back into the fragments they came from.

Splitting a merged config file normally shatters it: you get a heap of keys and no memory of which fragment owned them. silktouch takes it apart whole, so every piece returns where it came from, and combining puts it back exactly as it was.

## The problem

Some programs keep their configuration in one file that they also rewrite at runtime. One of them is probably open in another pane right now.

That is hostile to version control in both directions. You cannot hand author the file in modular pieces, because the program overwrites it wholesale. You cannot generate it from fragments either, because the next run would lose whatever the program wrote back.

The systemd drop in convention, `foo.d/*.json` merged into one effective file, solves the authoring half. Nothing solves the write back half. silktouch does both. It knows nothing about any particular application; `~/.claude/settings.json` is the case that prompted it, and it appears here as an example, not as a feature.

## Install

```
nix build      # produces ./result/bin/silktouch
nix develop    # a shell with cargo, clippy, rustfmt, rust-analyzer
```

Or run it straight from the flake: `nix run . -- combine --set claude`. A Nix install also places shell completions and `silktouch(1)`, both generated by running the binary the derivation just built, so they cannot drift from the CLI they describe. The man page is the full reference; this README is the tour.

## Quick start

```
$ cat frags/10-base.json
{ "permissions": { "allow": ["Bash", "Read"] }, "model": "claude-sonnet" }
$ cat frags/20-hooks.json
{ "hooks": { "PreToolUse": [] }, "permissions": { "allow": ["Write"] } }

$ silktouch combine --fragments frags -o settings.json
wrote settings.json
$ jq -c . settings.json
{"permissions":{"allow":["Bash","Read","Write"]},"model":"claude-sonnet","hooks":{"PreToolUse":[]}}
```

Run it again with nothing changed and it prints nothing. That is the rule of silence: a no op run is silent.

Now something external edits the output, a running program or your own hand. `diff` reports it and follows `diff(1)` exit codes, and `split` routes each change into the fragment that owns it:

```
$ silktouch diff --fragments frags -o settings.json
/permissions/allow  +"Edit"  -> 99-local.json
/model  ~"claude-opus"  -> 10-base.json
/oauthAccount  +{"id":"abc123"}  -> 99-local.json
$ echo $?
1

$ silktouch split --fragments frags -o settings.json
wrote frags/10-base.json
wrote frags/99-local.json
```

`10-base.json` now has `"model": "claude-opus"` in place. `20-hooks.json`, which never mentioned `model` or `oauthAccount`, was not touched at all.

## The four commands

- **`combine`**: fold the fragments into `--output`, in filename order, later fragments winning.
- **`split`**: read `--output` back and route every difference into the fragment that should own it.
- **`sync`**: `split` then `combine`. The order matters: combining first would silently discard whatever an external program had written since the last run. Pure CLI sugar; nothing in the library depends on it.
- **`diff`**: report what `split` would do, writing nothing, ever. Exit 0 when fragments and output agree, 1 when they differ, 2 on error. This is the one meant for a pre commit hook.

Every command takes either `--set NAME` or an explicit `--fragments DIR --output FILE`. `-o -` (`combine` only) writes to stdout and touches no files, which is what makes the engine pipeable.

## How it works

`combine` takes every `*.json` directly inside the fragment directory, not recursively, skipping dotfiles, sorted by filename as raw bytes. Numeric prefixes like `10-base.json` are a convention that happens to match byte order; the sort does not know about them. Objects recurse key by key, arrays follow the strategy for their path, and anything else lets the later fragment win outright.

`combine` is a pure function of the fragments, so `split` needs **no state file**. It recomputes `base`, the output `combine` would produce right now, and diffs that against the real output on disk. No lockfile, no snapshot, no cache directory.

| case | action |
|---|---|
| in both, both objects | recurse |
| in both, differing otherwise | overwrite at the **owner** |
| in the output only | insert into the **catch all** |
| in `base` only | delete from every fragment that declares it |

**Owner** is the last fragment, by filename sort, that declares a value at that exact path. The **catch all** absorbs anything with nowhere else to go: new keys and newly appended array elements. It defaults to `99-local.json`, is created on demand, and must sort after every other fragment, or `split` refuses to start and says which one is in the way.

Arrays need a rule, chosen per JSON Pointer path, where `*` matches one segment and the most specific match wins. **`concat-dedupe`** (the default) concatenates in fragment order and drops repeats by structural equality; `split` then routes elements by **membership**, not index. **`replace`** overwrites the whole array at the owner, like any scalar.

## The three laws

These are also, word for word, the crate's property tests.

- **A, inverse.** `split(F, combine(F)) == F`, byte identical.
- **B, absorption.** `combine(split(F, O)) == O`. Exact for objects and scalars. For arrays under `concat-dedupe` it holds only **up to element order**, because `combine` always emits elements in fragment order. Membership is what a drop in array means here.
- **C, idempotence.** `split(split(F, O), O) == split(F, O)`.

## Configuration

One `registry.toml`, found per the XDG Base Directory specification, or `--config PATH` to override discovery outright. silktouch writes nothing to `$XDG_STATE_HOME`, `$XDG_DATA_HOME` or `$XDG_CACHE_HOME` and never creates them: the stateless design leaves nothing to put there.

```toml
indent = 2
catch_all = "99-local.json"               # global default

[sets.claude]
fragments = "$DOTFILES/silktouch/claude"
output    = "~/.claude/settings.json"     # created, parent dirs and all
placement = "none"                        # or "symlink", with target = ...

[sets.claude.merge]
"/permissions/allow" = "concat-dedupe"    # the default, shown for clarity
"/some/ordered/list" = "replace"
```

Paths expand `~` and `$VARIABLES`. Every registry capability is reachable by flag, so `--set` is convenience, never a requirement.

## Comments in fragments

JSONC comments (`//` and `/* */`) are allowed in **source fragments**. The **combined output is always strict JSON**, full stop.

`comments = "forbid" | "protect" | "strip"` controls it, defaulting to `"forbid"` so nothing changes unless you opt in. The modes exist because `serde_json` discards comments when it parses, so a fragment `split` rewrites would lose them silently: `"protect"` turns that into an error, `"strip"` accepts the loss, and a fragment `split` never touches keeps its comments either way. JSON5 was rejected because its unquoted keys and single quoted strings would be silently rewritten into standard JSON on the first reserialise.

## Composing with GNU Stow

Stow and `placement = "symlink"` are alternatives, not rivals. Pick one per set. With `placement = "none"` silktouch touches only `output` and stow owns delivery into `$HOME`; keep fragments outside the stowed tree so stow never sees them.

If the target is already a real file a program has been writing for years, `stow --adopt` moves it into the package and leaves a symlink, preserving the contents. Then run `split` once to seed the fragments from it.

**Caveat, both placement modes.** Symlinked delivery assumes the program writes *through* the link rather than replacing it. One that replaces it leaves a regular file where the link was: stow conflicts on the next restow, and `placement = "symlink"` errors rather than clobbering. Verified only for Claude Code 2.1.259; assume nothing about other programs. Sidestep it entirely with `placement = "none"` and `output` pointed at the real path.

## Known limitation

If a fragment **and** the output both change between runs, `split` treats the fragments as base and the output as truth: the fragment side edit is overwritten silently. Detecting it would need a snapshot of the last `combine`, which is exactly the state the stateless design avoids. Run `sync` often, or run `diff` first and look.

## Library use

Library first, thin CLI second. `combine`, `split` and `diff` mirror the subcommands and take a `Config`. To embed with no filesystem at all, `combine_values` and `split_values` operate directly on `serde_json::Value` and a `FragmentSet`. `sync` is deliberately **not** in the library.
