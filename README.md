# silktouch

Bidirectional config fragment merger: `combine` folds JSON fragments into one file, `split` routes edits made to that file back into the fragments they came from.

Splitting a merged config file is normally destructive: you end up with a heap of keys and no memory of which fragment owned them, which list entries came from which layer, or what the program rewrote behind your back. silktouch splits it so every piece comes away intact and returns where it came from: values overwritten in place, new keys filed in the catch all, deletions propagated. Combining puts it back exactly as it was.

## The problem

Many programs keep their configuration in one file that the program itself also rewrites at runtime. That combination is hostile to version control in both directions: you cannot hand author the file in modular pieces, because the program overwrites it wholesale, and you cannot generate it from fragments, because you would lose whatever the program wrote back the next time it ran.

The systemd drop in convention (`foo.d/*.json`, merged into one effective file) solves the authoring half. Nothing solves the write back half. silktouch does both directions. It is a general purpose utility with no knowledge of any particular application: the motivating case is Claude Code's `~/.claude/settings.json`, which mixes hand authored config with keys the program rewrites at runtime, but that is an example in these docs, not a feature.

## Install

```
nix build      # produces ./result/bin/silktouch
nix develop    # a shell with cargo, clippy, rustfmt, rust-analyzer
```

or run it straight from the flake, without installing anything:

```
nix run . -- combine --set claude
```

A `nix build` (or a Nix based install of the package) also installs shell completions and the `silktouch(1)` man page. Both are generated by running the binary the derivation just built, so they can never drift from the CLI they describe.

## Quick start

A fragment directory:

```
$ cat frags/10-base.json
{
  "permissions": {
    "allow": ["Bash", "Read"]
  },
  "model": "claude-sonnet"
}
$ cat frags/20-hooks.json
{
  "hooks": {
    "PreToolUse": []
  },
  "permissions": {
    "allow": ["Write"]
  }
}
```

Combine them:

```
$ silktouch combine --fragments frags -o settings.json
wrote settings.json
$ cat settings.json
{
  "permissions": {
    "allow": [
      "Bash",
      "Read",
      "Write"
    ]
  },
  "model": "claude-sonnet",
  "hooks": {
    "PreToolUse": []
  }
}
```

Run it again with nothing changed. This is the rule of silence: a no op run prints nothing.

```
$ silktouch combine --fragments frags -o settings.json
$
```

Now something external edits `settings.json`, a running program, or your own hand:

```
$ jq '.permissions.allow += ["Edit"] | .model = "claude-opus" | .oauthAccount = {id: "abc123"}' \
    settings.json > tmp && mv tmp settings.json
```

`diff` reports it, following `diff(1)` exit codes:

```
$ silktouch diff --fragments frags -o settings.json
/permissions/allow  +"Edit"  -> 99-local.json
/model  ~"claude-opus"  -> 10-base.json
/oauthAccount  +{"id":"abc123"}  -> 99-local.json
$ echo $?
1
```

`split` routes each of those changes into the fragment that owns it, creating the catch all fragment if it doesn't exist yet:

```
$ silktouch split --fragments frags -o settings.json --verbose
wrote frags/10-base.json
wrote frags/99-local.json
  /permissions/allow  +"Edit"
  /model  ~"claude-opus"
  /oauthAccount  +{"id":"abc123"}
$ cat frags/99-local.json
{
  "permissions": {
    "allow": [
      "Edit"
    ]
  },
  "oauthAccount": {
    "id": "abc123"
  }
}
```

`frags/10-base.json` now has `"model": "claude-opus"` in place, and `frags/20-hooks.json`, which never mentioned `model` or `oauthAccount`, was not touched at all. `diff` now agrees:

```
$ silktouch diff --fragments frags -o settings.json
$ echo $?
0
```

## The four commands

- **`combine`**: fold the fragments into `--output`, in filename order, later fragments winning on conflicts.
- **`split`**: read `--output` back and route every difference into the fragment that should own it.
- **`sync`**: `split` then `combine`, in that order. It exists only because reversing the order is destructive: combining first would silently discard whatever an external program had written to the output since the last run. `sync` is sugar. Nothing in the library depends on it.
- **`diff`**: report the differences `split` would make, without writing anything, ever. It follows `diff(1)`: exit 0 when fragments and output agree, 1 when they differ, 2 on error. This is the one command meant to sit in a pre commit hook.

Every command takes either `--set NAME` (a registry set) or an explicit `--fragments DIR --output FILE` pair. `-o -` (`combine` only) writes the combined document to stdout and touches no files at all. This is what makes the engine pipeable and fully drivable without a filesystem:

```
$ silktouch combine --fragments frags -o - | jq .permissions.allow
```

## How combine works

`combine` discovers every `*.json` file directly inside the fragment directory (not recursively), skipping names starting with `.`, and sorts them by filename as raw bytes, a plain byte sort, not numeric or locale aware. Numeric prefixes (`10-base.json`, `99-local.json`) are a convention that happens to match byte order. The sort itself doesn't know about it.

Each fragment's root must be a JSON object. Anything else is an error naming the file. The fragments are then folded left to right:

- object + object: recurse, key by key
- array + array: resolved by the array strategy registered for that path (below)
- everything else, including a type mismatch: the later fragment wins outright

Output key order is first seen insertion order across the fold, not "whichever fragment touched it last", which is why silktouch requires `serde_json`'s `preserve_order` feature: without it, two runs over byte identical input could disagree on key order.

## How split works

`combine` is a pure, deterministic function of the fragments: the same fragment contents always produce the same output. That's the whole reason `split` needs **no state file**: it recomputes `base`, the output `combine` would produce right now, and diffs that against the real, possibly hand edited, output on disk. No lockfile, no snapshot of a previous run, no cache directory: the fragments and the output file are the only state that exists.

Each path is one of four cases:

| case | action |
|---|---|
| in both, both objects | recurse |
| in both, differing otherwise | overwrite at the **owner** |
| in the output only | insert into the **catch all** |
| in the fragments' base only | delete from every fragment that declares it |

**Owner** is the highest precedence fragment, the last one, by filename sort, that declares a value at that exact path. At least one does, by construction of `base`. An earlier fragment that also set the same path is left alone: it was already shadowed by the merge, and touching it again would change nothing observable.

The **catch all** absorbs anything with nowhere else to go: new keys, and newly appended array elements. It defaults to `99-local.json` and is created if it doesn't exist. Its filename must sort after every other fragment's, or `split` refuses to start and names the offending filename: otherwise whatever it just absorbed would be shadowed by that other fragment on the very next `combine`, silently breaking the round trip.

## Array strategies

Two arrays meeting at the same path need a rule, chosen per JSON Pointer path (`*` matches exactly one path segment, e.g. `/servers/*/args`, and the most specific match wins):

- **`concat-dedupe`** (default): concatenate in fragment order, dropping later occurrences of a value already seen by full structural equality. First occurrence fixes position.
- **`replace`**: the later fragment's array replaces the earlier one wholesale.

Under `concat-dedupe`, `split` routes array elements by **membership**, not index: an element in `base` but missing from the output is removed from every fragment that contributes it. An element in the output but not in `base` is appended to the catch all. Under `replace`, the whole array is simply overwritten at the owner, like any other scalar.

## The three laws

silktouch is designed to satisfy three laws. They are also, word for word, the crate's property tests:

- **A: inverse.** `split(F, combine(F)) == F`, byte identical. Splitting an output file nothing has touched since the last combine reproduces the fragments exactly.
- **B: absorption.** `combine(split(F, O)) == O`. An external edit survives the round trip. This holds exactly for objects and scalars. For arrays under `concat-dedupe` it holds only **up to element order**: `combine` always emits array elements in fragment order, so once an element has been spread across fragments (or newly appended to the catch all), the next `combine` reconstructs the same *set* of elements, not necessarily whatever order an external program last wrote them in. Membership is what a drop in style array means to silktouch. Ordering stops being meaningful once elements live in more than one fragment.
- **C: idempotence.** `split(split(F, O), O) == split(F, O)`. Running `split` twice against the same output has no further effect after the first run.

## Configuration

All configuration lives in one `registry.toml`, located per the XDG Base Directory specification on every platform:

- `$XDG_CONFIG_HOME/silktouch/registry.toml`, falling back to `~/.config/silktouch/registry.toml` when the variable is unset or not an absolute path.
- `$XDG_CONFIG_DIRS` is searched next, read only, in order: first match wins.
- `--config PATH` overrides discovery outright.

silktouch writes nothing to `$XDG_STATE_HOME`, `$XDG_DATA_HOME` or `$XDG_CACHE_HOME`, and never creates them: the stateless design leaves nothing to put there.

A worked example, covering the three ways a set's output can reach the program that reads it:

```toml
# $XDG_CONFIG_HOME/silktouch/registry.toml
indent = 2
catch_all = "99-local.json"          # global default

# A. silktouch owns the file outright, wherever you point it.
[sets.claude]
fragments = "$DOTFILES/silktouch/claude"
output    = "~/.claude/settings.json"     # created, parent dirs and all

[sets.claude.merge]
"/permissions/allow" = "concat-dedupe"    # the default, shown for clarity
"/some/ordered/list" = "replace"

# B. silktouch generates into the repo, stow places it.
[sets.nvim]
fragments = "$DOTFILES/silktouch/nvim"
output    = "$DOTFILES/nvim/.config/nvim/settings.json"
placement = "none"                        # default
catch_all = "zz-local.json"               # per set override

# C. silktouch generates into the repo and places it itself.
[sets.helix]
fragments = "$DOTFILES/silktouch/helix"
output    = "$DOTFILES/helix/.config/helix/config.json"
placement = "symlink"
target    = "~/.config/helix/config.json"
```

Paths expand `~` and `$VARIABLES`. Merge strategy keys and `--merge` flags share the same JSON Pointer + wildcard syntax.

Every registry capability is also reachable by flag. `--set NAME` is convenience, never a requirement:

```
silktouch combine --fragments d/ -o out.json --merge '/some/list=replace' --catch-all zz-local.json --indent 4
```

## Comments in fragments

JSONC comments (`//` and `/* */`) are allowed in **source fragments**. The **combined output is always comment free**: `combine`'s output is strict JSON, full stop.

This is controlled by `comments = "forbid" | "protect" | "strip"`, set globally or per set in the registry, or via `--comments`. The default is `"forbid"`: strict JSON everywhere, so nothing changes unless you opt in.

The reason the modes exist: `serde_json` discards comments when it parses, so a fragment `split` rewrites would silently lose any comments it had. `"protect"` turns that into an error instead of a silent loss. `"strip"` accepts the loss. A fragment that `split` never touches, read only, or simply left alone this run, keeps its comments regardless of mode.

JSON5 was deliberately not adopted for this: its unquoted keys and single quoted strings would be silently rewritten into standard double quoted JSON the moment silktouch reserialises the fragment, which is a worse surprise than requiring comments to be opted into explicitly.

## Shell completions and the man page

```
silktouch completions <bash|zsh|fish|elvish|powershell>
```

prints a static completion script to stdout. A Nix based install additionally wires up the *dynamic* completer (`COMPLETE=<shell>`), which calls back into the binary on every `<TAB>` and, unlike the static script, completes real `--set` names from your registry and `--merge` strategy names against the fixed list. `silktouch completions` stays available for anyone who wants the static script instead.

```
man silktouch
```

reads the man page. It's clap's own flag reference (generated from the same `Command` the CLI parses, so it can't drift) plus hand written sections covering what `--help` has no room for: the combine and split algorithms, array strategies, the three laws, exit statuses, file locations, the registry format, and worked examples. `silktouch man` prints the raw roff to stdout if you'd rather pipe it into `man -l -` or install it yourself.

## Composing with GNU Stow

Stow and silktouch's own `placement = "symlink"` are alternatives, not rivals: pick one per set, not both. With `placement = "none"` (the default), silktouch touches only `output` and stow owns delivery into `$HOME`. With `placement = "symlink"`, silktouch delivers the file itself and stow isn't involved.

Under `placement = "none"`, keep fragments **outside** the stowed tree so stow never sees them:

```
dotfiles/
  claude/                       # stow package
    .claude/
      settings.json             # stowed to ~/.claude/settings.json, written through
  silktouch/
    claude/                     # fragments, never stowed
      10-permissions.json
      20-hooks.json
      99-local.json
```

```toml
[sets.claude]
fragments = "$DOTFILES/silktouch/claude"
output    = "$DOTFILES/claude/.claude/settings.json"
```

Both paths sit inside the repo. In this mode silktouch never touches `$HOME`. Stow never touches the fragments.

**Bootstrap.** If the target already exists as a real file, a program has been writing to it for years and you're only now bringing it under version control, `stow --adopt claude` moves it into the package and leaves a symlink behind, preserving whatever the program had written. Then run `silktouch split --set claude` once to seed the fragments from its current contents.

**Caveat, applying to both placement modes.** Symlinked delivery assumes the foreign program writes *through* the link rather than replacing it. A program that replaces it leaves a regular file where the symlink was: stow will conflict on the next restow, and `placement = "symlink"` will error rather than clobber it. Resolve with `mv`. This has been verified only for Claude Code 2.1.258. Assume nothing about other programs until you've checked. Sidestep the question entirely with `placement = "none"` and `output` pointed straight at the real path.

## Known limitation

If a fragment **and** the output file both change between runs, `split` treats the fragments as base and the output as truth: the fragment side edit is overwritten silently. Detecting that would need a snapshot of the last `combine`, which is exactly the state the stateless design avoids. Mitigation: run `sync` often, or run `diff` first and look before routing anything.

## Library use

`silktouch` is a library first, thin CLI second. The three entry points mirror the subcommands:

```rust
use silktouch::{combine, split, diff, Config};

let cfg = Config { fragments: "frags".into(), ..Config::default() };
let outcome = combine(&cfg)?;   // writes `cfg.output`, reports what changed
split(&cfg)?;
diff(&cfg)?;
```

For embedding into something that already has the fragments and the output in memory, no filesystem at all, use `combine_values` and `split_values`, which operate directly on `serde_json::Value` and a `FragmentSet`. `sync` is deliberately **not** in the library: it is CLI sugar over `split` then `combine`, and nothing in the library depends on it.
